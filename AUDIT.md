# VoxMorph v6 - Audit & Improvement Roadmap

After a thorough examination of the `voxed.py` codebase, I have identified several critical design deficiencies and implementation flaws that prevent it from being a truly robust tool for "multi-GB" audio files.

## 1. Critical Design Flaws

### A. Memory Inefficiency (The "GB-Killer")
- **Issue**: The script uses `wavfile.read(args.input)`, which loads the **entire** audio file into RAM as a single NumPy array. For a multi-GB file (e.g., 4GB FLAC), this will likely cause an `MemoryError` on most consumer machines.
- **Fix**: Implement **Streaming I/O**. Read and process chunks directly from the disk or a memory-mapped file using `numpy.memmap` or a generator-based reader.

### B. Incomplete Parallelization
- **Issue**: While `process_large_file` uses `ProcessPoolExecutor`, the chunking and initial STFT/ISTFT logic within `apply_voice_morph_chunk` is efficient, but the heavy lifting of `get_lpc_poles` is called in a loop *inside* each chunk. This is better than single-threading the whole file, but processing very large chunks still creates a bottleneck.
- **Fix**: Optimize the inner loops of `apply_voice_morph_chunk` with vectorized NumPy operations where possible.

### C. Reassembly Artifacts (Phase & Windowing)
- **Issue**: The current reassembly uses a Hann window on the processed time-domain chunks. However, `apply_voice_morph_chunk` *already* performs its own STFT/ISTFT with Hann windows. Applying a second Hann window during reassembly and dividing by weights is a double-windowing approach that can lead to spectral artifacts and phase discontinuities at chunk boundaries.
- **Fix**: Use a "Cross-fade" or "Seamless Overlap-Add" strategy that respects the internal STFT hop sizes.

### D. Glottal Pulse Aliasing
- **Issue**: The `generate_glottal_excitation` function generates pulses in the time domain by simple phase accumulation. At high `f0` or with jitter/shimmer, this can introduce aliasing if not band-limited.
- **Fix**: Implement a band-limited impulse train (BLIT) or use a higher internal sampling rate for excitation generation.

## 2. Implementation Errors & Omissions

### A. Lack of Input Validation
- **Issue**: The script assumes a sample rate of 44100Hz in `human_vocal_template` (`d=1/44100.0`), but doesn't verify the input file's actual sample rate. If a user provides a 48kHz or 96kHz file, the formants will be shifted incorrectly.
- **Fix**: Pass the actual `sr` to all template functions.

### B. Metallic/Voicing Interaction
- **Issue**: The `metallic` parameter simply blends the original magnitude back in. If `voicing` is also high, the resulting magnitude can exceed reasonable bounds before `tanh` saturation, leading to "pumping" artifacts.
- **Fix**: Implement a more sophisticated spectral masking or energy normalization step before re-synthesis.

### C. FFmpeg Dependency
- **Issue**: If FFmpeg is missing, the script exits immediately for FLACs but doesn't check for its existence before trying to run it.
- **Fix**: Add a pre-flight check for `ffmpeg` in the system path.

## 3. Recommended Roadmap

1.  **Refactor for Memory Mapping**: Replace `wavfile.read` with a memory-mapped approach for large WAV files.
2.  **Sample Rate Awareness**: Correct the hardcoded 44100Hz values to use the input file's actual sample rate.
3.  **Refine OLA Reassembly**: Remove the double-windowing. Use a simple overlap-add with a constant-overlap-add (COLA) compliant window if possible, or a simple cross-fade.
4.  **Vectorize LPC**: Replace the manual loop in `apply_voice_morph_chunk` with a vectorized approach if possible, or at least optimize the frame-slicing.
5.  **Robust Error Handling**: Add checks for empty files, unsupported bit depths, and missing dependencies.
